# 1. 需求背景

公司内部人力资源管理依赖 Excel 和纸质流程，存在数据分散、算薪效率低、审批不透明等问题。本系统旨在建立统一的员工数字化档案，实现入转调离全流程线上化，提供管理后台与员工门户两端。

**五大用户角色：** HR 专员、部门主管、普通员工、财务专员、系统管理员。

**前端架构：** React 18 + TypeScript + Umi Max + Ant Design 5 + Zustand，管理后台与员工门户双端布局。

# 2. 详细设计

## 2.1 前端迭代目标

本次迭代交付 HRMS V1.0 前端全量，我负责的部分包括：

1. **全局工程基座**：项目目录结构、全局请求封装（Token 自动携带 + 401 静默刷新 + 统一错误处理）、路由全局守卫
2. **登录模块**：登录表单、首次改密弹窗、记住登录、按角色跳转
3. **双端布局**：管理后台 AdminLayout（Sider + Header + 动态菜单）、员工门户 PortalLayout
4. **权限体系**：用户管理、角色管理、菜单/权限管理、动态路由、按钮级权限、字段级权限（`<FieldGuard>`）
5. **组织架构**：部门管理（部门树 + 增删改查 + 合并）、职位管理（M/P/S 序列 + CRUD）
6. **Dashboard 工作台**：KPI 卡片 + 快捷入口 + 访问趋势图 + 最近操作

## 2.2 迭代具体描述

### 2.2.1 登录页面（`/login`）

##### UI&交互

PRD 内嵌原型图。居中卡片式登录表单，全屏无布局。

##### 前端逻辑

```
登录流程：
  ① 用户输入 username + password → 点击登录
  ② POST /auth/login → 获取 accessToken + refreshToken
  ③ 存入 localStorage + useUserStore
  ④ GET /auth/profile → 获取用户信息 + 权限码 + dataScope
  ⑤ 判断 mustChangePassword：
     ├── true → 弹出改密弹窗 → PUT /auth/password → 成功后跳转首页
     └── false → 直接按角色跳转
        ├── EMPLOYEE → /portal/profile
        └── 其他管理角色 → /admin/workbench

401/Token 过期：
  ① 拦截 401 → 尝试 POST /auth/refresh
  ② 成功 → 续签 Token，重发原请求
  ③ 失败 → 清除登录态 → 跳转 /login
```

###### 表单字段

| 字段名称 | 输入方式 | 是否必填 | 校验规则 | 提示文案 |
|---------|---------|---------|---------|---------|
| username | Input | Y | 11 位手机号或工号格式 | 请输入账号 |
| password | Input.Password | Y | ≥8 位 | 请输入密码 |
| 记住登录 | Checkbox | N | — | localStorage 存储 username |

改密弹窗字段：

| 字段名称 | 输入方式 | 是否必填 | 校验规则 |
|---------|---------|---------|---------|
| oldPassword | Input.Password | Y | 非空校验（后端 BCrypt 对比 password_hash） |
| newPassword | Input.Password | Y | ≥8位，含大小写字母+数字 |
| confirmPassword | Input.Password | Y | 须与 newPassword 一致 |

###### 操作按钮

| 名称 | 交互 | 是否有二次确认 | 显示控制 |
|------|------|---------------|---------|
| 登录 | 点击调用 POST /auth/login | N | 始终显示 |
| 确认改密 | 点击调用 PUT /auth/password | N | mustChangePassword=true 时弹出 |

##### 所需API(返回json)

| 方法 | 地址 | 说明 |
|------|------|------|
| POST | `/auth/login` | 登录 → `{ accessToken, refreshToken, expiresIn, mustChangePassword }` |
| POST | `/auth/refresh` | 刷新 Token（401 时静默调用）|
| GET | `/auth/profile` | 当前用户信息 + 权限码 + dataScope |
| PUT | `/auth/password` | 修改密码 |

### 2.2.8 菜单/权限页面

##### UI&交互

无独立页面，权限的分配集成在角色管理页面的权限分配 Modal 中。

##### 前端逻辑

```
权限数据来源：后端 sys_permission 表
前端通过 GET /system/roles/{id}/permissions 查询当前角色的权限 ID 列表

权限树渲染规则：
  ├── 按 module 分组为一级节点
  ├── type=MENU → 可展开的菜单节点
  ├── type=BUTTON → 叶子节点（按钮级权限）
  └── type=API → 叶子节点（接口级权限）

动态路由联动：
  config/routes.ts 中每个路由配置 access 字段
  例如：{ path: '/admin/system', access: 'canAdmin', routes: [...] }
  Umi access 插件根据 permissions[] 自动过滤
```

### 2.2.10 全局 Token 管理与无操作超时自动登出

> **对应 PRD §11.2** — 30 分钟无操作自动登出  
> **对应后端系分 §3.2.5 / §4.3** — 双 Token 安全机制

##### 设计目标

在不影响用户体验的前提下，满足 PRD 的"30 分钟无操作自动登出"安全要求。核心思路：

> **accessToken 有效期 ≠ 无操作超时，两者是独立参数：**

| 参数 | 值 | 意图 |
|------|----|------|
| accessToken 有效期 | **2 小时** | 控制 token 刷新频率，减轻后端 refresh 压力 |
| 无操作超时阈值 | **30 分钟** | 满足 PRD §11.2 安全要求 |

**为什么 accessToken 设 2 小时而不是 30 分钟？**
- 30 分钟意味着用户每 ~29 分钟就要调一次 refresh API，连续工作 8 小时需刷新约 16 次
- 2 小时则只需刷新约 4 次，后端压力降至 **1/4**
- 无操作登出不依赖 accessToken 过期，而由 idleDetector + Redis 独立保障
- 2 小时被盗窗口期对于企业内部 HR 系统仍然可接受（非金融级）

**解决方案：主动预判刷新 + Idle Detector + 401 拦截器兜底，三层联动。**

---

##### 架构总览

```
┌──────────────────────────────────────────────────────────────────┐
│                     三层 Token 管理架构                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                    │
│  ① 主动预判刷新（覆盖 99% 场景）                                    │
│     ┌───────────────────────────────────────┐                     │
│     │ 登录后解码 JWT 拿到 exp               │                     │
│     │ 在过期前 60s → 静默调 /auth/refresh   │                     │
│     │ 拿到新 token → 再调度下一轮            │                     │
│     └───────────────────────────────────────┘                     │
│         ↓ 万一翻车（浏览器休眠、tab 后台）                          │
│  ② 请求拦截器兜底（覆盖剩余 1%）                                    │
│     ┌───────────────────────────────────────┐                     │
│     │ 某请求返回 401 → 拦截，不抛给页面       │                     │
│     │ 排队锁：同时 N 个 401 只刷 1 次 refresh │                     │
│     │ 排队请求拿新 token 重放                │                     │
│     └───────────────────────────────────────┘                     │
│         ↓ refresh 也失败                                           │
│  ③ 兜底 → 清登录态 → 跳 /login                                    │
│                                                                    │
│  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─                         │
│                                                                    │
│  ④ Idle Detector（横切 ①~③）                                       │
│     监听 mousemove/keydown/click/scroll                            │
│     30 分钟无操作 → 强制登出，优先级高于主动刷新                      │
└──────────────────────────────────────────────────────────────────┘
```

##### 1. 主动预判刷新（`tokenRefresher.ts`）

JWT 的 payload 是 base64 编码，前端可以直接解码读取 `exp` 字段，无需校验签名：

```typescript
// 解码 JWT payload
function decodeJwtPayload(token: string): any {
  const payloadBase64 = token.split('.')[1];
  return JSON.parse(atob(payloadBase64));
}

// 计算剩余秒数
function getTokenRemainingSeconds(token: string): number {
  const payload = decodeJwtPayload(token);
  return payload.exp - Math.floor(Date.now() / 1000);
}
```

**调度逻辑：**

```
登录成功
  ↓
解码 accessToken，读到 exp
  ↓
计算剩余时间，设 setTimeout
  ↓
时间到 → 检查 idleDetector：用户是否在操作？
  ├── 是 → POST /auth/refresh → 拿新 token → 调度下一轮
  └── 否 → 不刷新，等待 idleDetector 触发登出
```

**关键规则：** 调度间隔取 `min(提前60s刷新, idle剩余时间)`，确保 idle 超时优先于 token 刷新。

---

##### 2. Idle Detector（`idleDetector.ts`）

监听浏览器的用户交互事件，记录"最后活跃时间"：

| 监听事件 | 说明 |
|---------|------|
| `mousemove` | 鼠标移动 |
| `mousedown` | 鼠标点击 |
| `keydown` | 键盘输入 |
| `scroll` | 页面滚动 |
| `touchstart` | 触屏操作 |
| `click` | 元素点击 |

**实现要点：**

```typescript
const IDLE_TIMEOUT = 30 * 60 * 1000; // 30 分钟
let lastActivityTime = Date.now();

// 用户操作时刷新最后活跃时间
window.addEventListener('mousemove', () => { lastActivityTime = Date.now(); }, { passive: true });
window.addEventListener('keydown', () => { lastActivityTime = Date.now(); }, { passive: true });
// ... 其他事件同理

// 每 10 秒检查一次
setInterval(() => {
  if (Date.now() - lastActivityTime >= IDLE_TIMEOUT) {
    forceLogout('30分钟无操作');
  }
}, 10_000);
```

**Idle Detector 与主动刷新的关系：**
- 主动刷新前先问 idleDetector：用户 idle 了吗？
- idle 了 → 不清 refresh、不清 timer，静待 idleDetector 触发登出
- 未 idle → 正常刷新

---

##### 3. 401 拦截器排队重放（`app.tsx` responseInterceptors）

当主动刷新失效（如浏览器休眠后唤醒），某请求走到后端返回 401 时，拦截器处理：

```
收到 401
  ↓
是 /auth/refresh 接口本身的 401？
  ├── 是 → refreshToken 也过期了 → 跳登录页
  └── 否 → 进入排队刷新逻辑
          ↓
  已经有请求在刷新了？
  ├── 是 → 排队等待，等新 token 出来后重放
  └── 否 → 成为"刷新者"
          ↓
  发起 POST /auth/refresh
  ├── 成功 → 更新本地 token → 重放当前请求 + 放行排队队列
  └── 失败 → 清登录态 → 跳登录页
```

**排队锁机制（防止并发刷新）：**

```typescript
let isRefreshing = false;
let pendingQueue: Array<{
  resolve: (token: string) => void;
  reject: (err: any) => void;
}> = [];

// 第一个触发 401 的请求负责刷新
isRefreshing = true;
const newTokens = await post('/auth/refresh', { refreshToken });

// 重放当前请求
config.headers.Authorization = `Bearer ${newTokens.accessToken}`;

// 放行所有排队的
pendingQueue.forEach(p => p.resolve(newTokens.accessToken));
pendingQueue = [];
```

这样同时到达的 N 个请求只产生 1 次 refresh 调用，页面数据不丢失、不闪烁。

---

##### 4. 用户会话生命周期时序

```
09:00  用户登录
       ├── tokenRefresher.scheduleNext() → 调度 10:59 刷新
       └── idleDetector.start() → 开始监听操作

09:00~10:57  用户一直在操作
             mousemove → lastActivityTime 不断更新

10:59  主动刷新触发
       ├── idleDetector.getIdleRemainingMs() ≈ 32 分钟 → 未 idle
       └── POST /auth/refresh 成功 → 新 token exp=12:59 → 调度下一轮

（中场休息）
10:57  用户离开工位（停止操作）
       lastActivityTime = 10:57

11:27  idleDetector 扫到：当前 11:27 - last 10:57 = 30 分钟
       → forceLogout('30分钟无操作')
       → 清 token → 清 timer → 跳 /login

12:59  用户的旧 token 过期
       但此时用户已经被登出约 1.5 小时了，页面在登录页
```

> **关键差异：** accessToken 有效期的 2 小时只决定了刷新频率（每 ~2h 刷一次）；无操作超时 30 分钟由 idleDetector（前端）+ Redis `user:last-active`（后端）独立保障，两者互不干扰。

| 项 | 方案 |

**全局业务错误码处理：**

| code | 处理方式 | 说明 |
|------|---------|------|
| 0 | 正常返回 `data` | 成功 |
| 10001 | `message.error('参数校验失败')` | 参数错误 |

| 20002 | `message.warning('无权限')` | 角色权限不足 |
| 20003 | `message.warning('字段权限不足')` | 敏感字段不可见 |
| 30001~60004 | `message.error(后端返回的 message)` | 业务拒绝，显示具体原因 |

```typescript
function handle401() {
  // Token 过期 → 清除登录态 → 跳转登录
  localStorage.removeItem('accessToken');
  localStorage.removeItem('refreshToken');
  useUserStore.getState().reset();
  window.location.href = '/login';
}
```

| HTTP | 前端处理 |
|------|---------|
| 401 | `handle401()` |
| 403 | `message.error('无权限访问')` |
| 422 | `message.error(response.data.message)` |
| 500 | `message.error('系统内部错误')` |
